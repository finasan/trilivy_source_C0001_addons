Deployment Guides: a control panel of step-by-step deployment cases

A new add-on, guides, for the people who deploy Trilivy at a client: a splash page with one tile per case (for example "Knowledge assistant from documents" or "Connect an app"), each a step-by-step guide that opens the real pages, says exactly what to do, and checks that it worked.

Your answers: every client gets it, launched on c0002 first, I draft the cases, steps are checked automatically.

1. Short answer

  • Yes, on c0002, and the Demo stays on. The Demo add-on only acts on prospect accounts (account_type = 'demo_user', see lib/Demo.cfc sessionDemo()). Staff and admin accounts on c0002 already see the plain platform. The guides are for those accounts, so the two never meet.
  • Separate add-on, not a Demo mode. The Demo locks and sells; the guides open everything and instruct. Mixing them would make every change to one a risk for the other. Same isolation idea as AgentFactory_V2: own folder /home/trlv_addons/guides, own tables cx_guide_*, own database addon_guides.
  • The story engine is copied, not shared. Slides, live steps with a coach panel, Back/Next and progress already work in the Demo (Quick Start). The guides start from a copy of that code and extend it with checks, run variables and team progress.
  • "To all clients" is new for add-ons. Today add-ons are internal-only (the header of trlv_addon.py says so) and are installed one client at a time. Section 4 lists the small fleet changes: an "every client" flag, install on all, and auto-install on new boxes.

Runs: progress per deployment, not per person

Starting a guide creates a run: a name ("ACME HR assistant"), the values it needs (instance, knowledge base, client contact…), the person in charge, and a status for every step. Anyone with access can open the run and carry on. The run page doubles as a deployment record: who did what, when, every check result, and a printable summary to hand to the client.

3. c0002: launched next to the Demo

  • Who sees what on c0002. Prospects (demo_user) never see the guides; the Demo's menu filter hides the Deployment Guides entry like any other non-demo item. Staff and client admins see the guides; the Demo does nothing to them.
  • Turning the Demo off is possible but not needed. Removing it on the fleet Add-ons page drops its hooks and keeps addon_demo. Nothing in the guides depends on it.
  • Optional: a public showroom. Since c0002 is where prospects arrive, the guides' catalogue (tiles and overviews only, read-only, no runs) can be offered to prospects as a Demo story step or DEMO-bar link: "See how a deployment works". That shows a buyer the rollout is organised. See decision D3.
One caution. c0002 is also the Demo's dev box: edited live, snapshotted to c0002-work, Demo data in its instances. Guides written and tested there create real instances and knowledge bases. Rule: test runs use the prefix GTEST_, and the guide console has a Clean up this test run button that removes exactly what that run created (it knows from the run's values). Real customer deployments run on the customer's own box, never on c0002.

4. Getting it to every client

Today an add-on goes to one client at a time: trlv_addon.py install <name> <version> <client> → playbook 19, recorded in flt_company_addon. To make "every client" safe and automatic:

  1. addon.json gets "scope": "all_clients" (the Demo stays "internal"). The build refuses an all-clients add-on that contains anything internal. The secret scan already runs.
  2. "requires_platform": "1.01.0021": playbook 19 refuses to install on an older box, and the fleet Add-ons page shows "needs upgrade first". The guides point at real pages, so they must match the platform they run on.
  3. Fleet Add-ons page: "Install on all clients", one box after another with stop-on-first-failure. It uses the same playbook and the same live-vs-installed column you already have.
  4. New boxes get it automatically. The provisioning run calls playbook 19 for every all_clients add-on after the platform is in. That's playbook 17's path, so per the fresh-install lesson it gets tested on a never-touched box.
  5. Upgrades. After a platform upgrade (trlv-upgrade), the box re-checks requires_platform and the guides' page list (section 10), and flags guides that need a new version.

Content flow: written in the guide console on c0002 → Export → seed-pull guides c0002 commits it to /home/trlv_addons/guides/seed/ → build → install on all. This is the same loop as the Demo. Runs (progress, check results) are box data: they stay on each client and are never exported or overwritten by an install.

Should it be in the core release instead? I advise against it. As an add-on, guide content can be fixed the same day without a platform release, and you keep cutting releases only for platform changes.

7. Automatic checks

Rule: a guide never contains SQL or code. It names a check from a fixed library, written in guides/lib/Checks.cfc and reviewed like any code, with arguments taken from the run ({"instance":"{instance}","min":50}). Every check is read-only, returns ok / fail / unknown + a sentence + a "fix it here" link, and times out after 10 s. A content editor cannot make a box run anything new.

10. Risks and how the plan handles them

  • Guides go stale when pages move. This is the biggest risk. Every step stores its page address. A self-test in the console (and after every platform upgrade) runs page_reachable on every address and the check library's own probes, and lists broken steps by guide. A broken step shows "this step needs an update" instead of a dead link.
  • A check that lies is worse than no check. Checks are read-only, never green on "unknown", and covered by a test that makes each one fail on purpose (Phase 1).
  • Test data on c0002. GTEST_ prefix plus a clean-up limited to what the run itself created. It never touches Demo instances.
  • The first all-clients add-on. Install on all stops on the first failure. Removing it keeps runs (remove without --purge-data), so a client never loses its deployment record.
  • Language. English first. The tables carry no language column yet; if you want more languages later, it's added like the Demo's lang. See D4.

11. Decisions for you

  1. D1 · Name in the menu. "Deployment Guides" (recommended), "Setup Guides", or "Go-Live Center".
  2. D2 · Who may run guides on a client box. Admin and operator roles (recommended), or every signed-in staff user.
  3. D3 · Public showroom on c0002. Show prospects the read-only catalogue from the Demo ("See how a deployment works")? I recommend yes, after Wave 1.
  4. D4 · Languages. English only for now (recommended), or build the language column in from day one.
  5. D5 · Wave 1 order. G1 First day, G2 Knowledge assistant, G3 SharePoint sync, G4 Quality before go-live (recommended). Change or swap in G5–G8?
  6. D6 · Client edits. Content is read-only on client boxes (recommended). Or may a client add its own local steps or notes to a guide (kept apart from ours so an install never overwrites them)?
Once these are answered, Phase 0 + 1 can start. Nothing has been coded or changed for this plan.
